## 0. 需优先向老师确认：二体式结构与上传内容

最终产品形态已确定为二体式：

- 探头负责贴胸采集、模拟前端、ADC 和心音预处理。
- 主机负责 AI 推理、显示、播放、无线通信和服务器上传。

- 探头与主机使用 BLE 无线，还是使用有线连接。

## 1. 一句话介绍

本项目面向心音采集与分析，构建一套从接触式心音传感器、嵌入式采集与
无线传输，到上位机心音 AI 推理和结果展示的便携式系统。

当前工作重点不是先堆叠功能，而是先把传感器、ADC、MCU、帧格式和无线
链路之间的接口定义清楚，保证数据不失真、不丢样、可验证，并为后续
S1/S2 识别和杂音风险分析提供稳定输入。

## 系统架构

### 总体关系

探头和主机组成便携式设备，服务器是外部平台。主机必须能在没有服务器的
情况下完成采集、显示、播放和初步诊断。

```text
探头（贴胸口）
  -> BLE / 有线
主机（AI + 屏幕 + 扬声器 + WiFi）
  -> WiFi / 手机网关
服务器（数据存储）
```

### 探头

探头只负责可靠采集和预处理，不做 AI、不显示、不播放。

- Piezo/PVDF 或麦克风传感器，配套声耦合、外壳和防震结构。
- 模拟前端完成放大、20 Hz 高通、1 kHz 低通、抗混叠和偏置。
- 外部低噪声 ADC 通过 I2S 或 SPI 输出。
- 低功耗 MCU/DSP 完成 ADC 采集、滤波、降噪和抽取。
- 固件按 8 kHz、16-bit、单声道连续采集，并输出 4 kHz 或 8 kHz PCM。
- 默认 4 kHz 输出的 20 ms 数据量为 80 samples、160 B、64 kbps。
- 20 ms 分帧，生成 `sequence` 和 `timestamp_ms`，计算 CRC 后输出固定帧。
- 通过 BLE 或有线接口发送数据；不建议探头直接连接服务器。

### 主机

主机是设备的控制、AI、显示和联网中心。

- 通过 BLE 或有线接口接收探头数据，完成分片重组、CRC 和丢帧检测。
- 缓存 2 到 5 秒心音窗口，运行 int8 量化 AI 模型。
- 输出诊断类别、置信度和模型版本，不重新生成探头时间戳。
- 驱动 LCD 显示波形、BPM、AI 结果和信号质量。
- 驱动扬声器回放心音，并通过 WiFi 上传数据到服务器。
- 断网时本地缓存，恢复后补传；负责 OTA、电量和设备状态管理。
- 优先通过 WiFi 连接服务器，也可以选配手机 App 作为 BLE 网关。

### 服务器

服务器当前只负责数据存储，不参与实时诊断。

- 数据库保存设备、会话、数据索引和 AI 结果等结构化信息。
- 对象存储保存原始心音、压缩音频、特征文件或波形数据。
- 提供最基础的上传接口、数据索引和读取/导出接口。
- 保留设备身份和访问控制，避免数据被未授权读取。
- 当前范围不包含模型训练、模型管理、OTA 分发和复杂 Web GUI。

### 通信链路

探头到主机：

- 二体式探头与主机优先使用 BLE 5.0 GATT 自定义服务。
- 如果老师选择有线连接，则改用 UART、SPI、I2S 或 USB-C/pogo pin。
- BLE 每 40 到 100 ms 批量打包，不逐样本发送。
- MTU 建议协商到约 247 B，音频帧允许分片。
- 应用层必须包含 `sequence`、分片序号、分片总数和 CRC16。

主机到服务器：

| 数据类型 | 推荐协议 |
| --- | --- |
| 设备注册、会话、数据查询 | HTTPS REST |
| AI 结果、状态和告警 | HTTPS REST 或批量上传 |
| 原始心音、特征和批量文件 | HTTPS 上传或对象存储预签名 URL |

最终推荐架构：

```text
探头：传感器 + AFE + ADC + DSP + BLE
主机：BLE 接收 + AI + LCD + 扬声器 + WiFi
服务器：数据存储
```

## 2. 当前阶段

阶段 0：数据与硬件接口冻结。

本阶段的交付物是一份双方共同认可的“接口合同”，需要明确：

- 传感器输出什么信号，有效带宽是多少。
- ADC 如何把数据交给 MCU，是否可能丢样。
- MCU 以什么采样率、帧长、数据类型和时间信息发送数据。
- 上位机如何判断帧边界、顺序、时间戳和损坏。
- MCU 的 RAM、Flash、DMA 是否能支持采集、协议、屏幕、无线和 AI 需求。
- 屏幕、无线模块和 ADC 是否争用同一条通信接口。

## 3. 已形成的技术基线

### 3.1 信号与采样

| 项目 | 当前基线 | 说明 |
| --- | --- | --- |
| 目标信号 | 心音 S1/S2 | 重点保留低频能量 |
| 有效带宽 | 20-1000 Hz | 这是信号带宽，不是采样率 |
| 传感器 | 优先 piezo/PVDF；MEMS/Mic 备选 | MEMS 必须核对低频截止和 20-1000 Hz 频响 |
| 采集格式 | 8 kHz、单声道、16-bit PCM、小端 | 为抗混叠和后续抽取保留余量 |
| AI 输入 | 4 kHz | 先带限，再 2:1 抽取，不能直接把 8 kHz 数组当 4 kHz 使用 |
| 回放策略 | 默认保存 8 kHz | 若要求自然人声或环境音频，需要另行确认是否采 16 kHz |

### 3.2 数据链路

```text
传感器
  -> 模拟前端：增益、偏置、抗混叠
  -> ADC + DMA：8 kHz、16-bit、连续采集
  -> MCU：环形缓冲、20 ms 组帧
  -> 协议层：sequence、timestamp、CRC16
  -> 无线 / 本地存储 / 屏幕
  -> 上位机：解码、校验、带限与 2:1 抽取
  -> AI：S1/S2、杂音风险、结果报告
```

### 3.3 数据上传与服务端链路

现有材料明确的是“设备到主机”的数据契约，还没有定义“主机或网关到
服务器”的上传契约。服务端不应被当作隐含功能，需要在阶段 0 或紧接着的
阶段 1 中明确接口。

建议的最小端到端链路：

```text
探头 4 kHz / 8 kHz 原始帧
  -> BLE / 有线
  -> 主机：接收、缓存和本地 AI 推理
  -> WiFi / 手机网关
  -> 会话聚合、CRC 和丢帧检查
  -> HTTPS
  -> 服务器：设备认证、会话与元数据存储
  -> 原始数据 / 特征 / 本地 AI 推理结果
  -> 数据库、对象存储和按需读取
```

AI 推理位置已确定为本地主机：

- 本地主机负责信号处理、模型推理和结果生成，是唯一的 AI 推理位置。
- 服务器不运行模型，也不重新解释推理结果。
- 如需上传服务器，服务器只负责数据接收、结构化索引和文件存储。
- 上传内容可以是原始数据、特征或本地推理结果，但仍需产品侧确认。

上传数据量参考：

| 项目 | 结果 |
| --- | ---: |
| PCM 纯负载 | 320 B / 20 ms = 16 kB/s |
| 纯 PCM 每分钟 | 约 0.96 MB/min |
| 含 30 B header + 2 B CRC 的帧 | 352 B / 20 ms = 17.6 kB/s |
| 含协议开销每分钟 | 约 1.056 MB/min |

如果连续上传原始 8 kHz PCM，一分钟约 1 MB，长时间会话必须考虑流量、
存储、断网重传和隐私。更合理的方式通常是由本地端按测量会话聚合后上传，
而不是把每一帧直接变成一次 HTTP 请求。

服务端链路至少需要定义：

- 上传单位：逐帧流式上传，还是按一次测量会话批量上传。
- 上传内容：8 kHz 原始 PCM、4 kHz AI 输入、特征数据，还是仅结果摘要。
- 会话元数据：设备 ID、会话 ID、采样率、位深、声道数、帧长、时长、
  sequence 范围、CRC/丢帧统计。
- 传输协议：HTTPS REST，以及断网后的缓存和重传策略。
- 认证授权：设备认证、用户身份、访问控制和数据隔离。
- 隐私与合规：是否需要匿名化、加密存储、用户授权、保留期限和删除机制。
- 时间基准：设备时间戳、主机接收时间和服务器记录时间分别如何保存。
- 版本管理：协议版本、模型版本、特征版本和结果格式版本。

### 3.4 帧与协议

| 项目 | 当前值 |
| --- | --- |
| 逻辑帧长 | 20 ms |
| 每帧样本数 | 160 samples/channel |
| PCM 负载 | 320 B |
| 协议头 | 30 B |
| CRC | 2 B |
| 单帧完整长度 | 352 B |
| 采样格式 | `int16_t` PCM，小端 |
| 序列号 | `uint32_t`，每帧递增 1，自然回绕 |
| 时间戳 | `uint32_t`，单位 ms，表示首样本采集时刻 |
| CRC | `CRC-16/CCITT-FALSE` |

固定测试向量：

- `version = 1`
- `flags = 0x01`
- `header_bytes = 30`
- `codec = 1`
- `channels = 1`
- `bits_per_sample = 16`
- `sample_rate_hz = 8000`
- `frame_samples = 160`
- `sequence = 1`
- `timestamp_ms = 1000`
- `payload_bytes = 320`
- payload 为 160 个零样本，共 320 个 `0x00`
- 期望 CRC：`0x7B5E`
- 线上 CRC 字节：`5E 7B`

## 4. 关键设计理由

- 选择 8 kHz，而不是只采 4 kHz，是为了给抗混叠滤波、时间分辨率和后续
  算法留出余量。
- 选择 4 kHz 作为 AI 输入，是因为 20-1000 Hz 信号经 8 kHz 采集后可以
  通过带限和 2:1 抽取稳定得到，不能直接改变采样率语义。
- 选择 20 ms 逻辑帧，是因为它在传输延迟、缓冲大小和 BLE 分片之间比较
  平衡；160 samples 对 8 kHz 正好是 20 ms。
- 传输使用 `int16_t` PCM 和小端格式，不发送 `float32`，可以减少带宽、
  功耗和跨平台兼容问题。
- 时间戳定义为“首样本采集时刻”，不是发送或接收时刻，因此无线发送
  抖动不能写入时间戳。
- 协议使用固定字节布局，不直接发送带编译器 padding 的 C 结构体。
- 采集链路禁止阻塞式逐样读取；每帧处理函数只消费已经完整写入的缓冲。
- 屏幕、无线和 ADC 最优先使用独立总线；如果必须共享，需要独立 CS、
  总线锁、可协商速率和实测最大阻塞时间。

- 为什么采用固定字节布局，而不是直接发送 C 结构体
- 为什么 ADC 不能使用阻塞式逐样读取
