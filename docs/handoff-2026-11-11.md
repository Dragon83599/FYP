## 1. 这个项目到底是什么

### 1.1 两条线，别搞混

仓库里有**两条方向**，时间是分界的：2026-10 及以前是一条，ADR-020 之后换成另一条。

| | 旧线（2026-10 及以前）| **新线（当前主线）** |
| --- | --- | --- |
| 问题 | 二体式无线听诊器 + 杂音（murmur）二分类筛查 | **五分类瓣膜病（AS/MS/MR/MVP/N）单标签分类** |
| 证据 | CirCor 1.0.3，874 人患者级 5 折 | **Yaseen 1,000 条**，录音级 5 折 + 15% holdout |
| 交付 | ESP32-S3 主机固件 + BLE LKA1 链路 + 屏 | **PWA（手机浏览器）单轨**，TF.js 推理 |
| 状态 | **PC 侧证据链完成，缺上板实测**（没买板子，ADR-017）| **进行中**（W3）|
| ADR | ADR-001…018 | ADR-020…057 |
| 代码 | `firmware/`、`shared/`、`tools/audio-sim/`、`pwa/bluetooth.js` 等 | `tools/ai/`（w3_arms / repro_ma2023 / ssl_*）、`pwa/` |

**换方向的原因**（ADR-020）：旧线没有上板数据、只有单一数据集、且匿名评审最看重的
"跨库泛化"无从谈起；新线有一个公开基准 + 一篇可 1:1 复现的论文（Ma 2023）。

**旧线没有废弃**：`firmware/` 能编译、`npm run sim:demo` 能跑、BLE 链路已用 ESP32-S3 模拟探头
实测过（MTU 247、2M PHY、16,000 帧**零丢帧**）。它是"工程可行性"的证据，不是主线。

### 1.2 新主线的产品形态

```
8 kHz 心音 → 预处理（1 kHz、2 s、2,000 点、min-max）→ 20,193 参数 1D-CNN → 5 类概率
                                                              ↓
                                                   手机浏览器（PWA，TF.js/WebGL）
```

- **已部署**：<https://dragon83599.github.io/FYP/>（GitHub Pages，源分支 `pwa-export`）
- **已真机验证**：安卓 Edge + WebGL，端到端概率最大差 **1.88e-12**，纯推理**中位 4.4 ms / P95 5.1 ms**
  （判据中位 ≤1 s、P95 ≤2 s，两个数量级余量）
- **可安装**：`manifest.json` + `sw.js` 预缓存 16 个文件，手机装完后**关电脑 + 飞行模式**仍可自检

### 5.4 W3 关键结果（`docs/w3-robustness.md`）

**（a）单一增强各自专精，没有全能**（10 个扰动条件，macro F1 %）

| 条件 | base | augS（只相位）| augB（全能型）|
| --- | ---: | ---: | ---: |
| clean | **97.90** | 96.31 | 87.90 |
| randstart（随机起点）| 53.67 | **95.71** | 87.79 |
| shift（循环平移）| 38.86 | **95.73** | 88.87 |
| noise:0.1 | 31.18 | 13.04 | **81.06** |
| hum（50 Hz）| 79.06 | 48.75 | **82.98** |

- `augS` 把相位问题从 53.67 拉到 95.71，但抗噪反而更差（31.18 → 13.04）
- **相位鲁棒性与抗噪能力在这个结构上是竞争关系**，组合（augC）没有叠加收益

**（b）最终配置（T4，2026-11-09 用户选定）**

**GAP + 纯噪声增强（σ ≤ 0.08）**：干净 **93.50** / 随机起点 **90.00** / σ=0.1 **85.59**。
干净通过线因此从 95 **下调到 93**（任何保持相位鲁棒的配置，干净精度都落在 92.8–93.5）。

**（c）SSL 的结论两次反转，这是最容易写错的一段**

| 版本 | 结论 | 条件 |
| --- | --- | --- |
| ADR-057 | SSL 增益 **+0.39**，CI [−1.19, +1.94] 跨 0 → **无效，不进主线** | **无增强基线** |
| §12（2026-11-10）| SSL **首次出现真实正增益**：干净 +1.21 / 随机起点 +0.95 / 工频 +6.06 | **有噪声增强的基线** |

**为什么反转**：抗噪能力本来就主要来自噪声增强（30.8 → 97.2），拿"无增强基线"去比论文的
噪声曲线是**错的对照**。代价是中等噪声下降（σ=0.1 **−3.14**，σ=0.15 −10.58）。

**（d）一个影响所有增强实验的实现缺陷**

增强的随机量此前**按批抽取**（标量），一个 batch 32 条共用一个 σ / 相位 / 增益，
**多样性只有设计值的 1/32**。已加入 `--aug-per-sample` 开关，但**默认关闭**以保持历史结果可复现。
**开启后所有增强类实验的数字都会变。**

## 7. 工作规则（硬约束，不是建议）

`AGENTS.md` 的要求对**每一次**代码/结论修改都有效。摘要：

1. **技术选型必须基于工程应用**，不能凭偏好或厂商宣传
2. 每个选择**至少 2 个可实施方案**，且必须包含"维持现状 / 不引入新组件"
3. 对比要覆盖：功能匹配、性能、功耗、成本、体积、开发难度、供应链、安全性、可靠性、可测试性、进度风险
4. **证据分级**：一手（标准/datasheet/官方文档/官方实测）> 独立实测（论文/公开项目）> 厂商宣称 > 工程估算
5. 关键决策**不能只凭估算冻结**，必须有验收方法、测试条件、失败判据、回退方案
6. 改接口/器件/协议/算法前**先查 ADR**；与旧结论冲突时**先更新证据和影响分析，不能静默修改**
7. 每项正式决策写进 `docs/engineering-decision-register.md`
8. 组会 PPT **必须含方案对比页**，不能只展示最终选择
9. 证据不足 → 标 **"候选方案" / "待实测"**，不能写"已冻结"
10. 新证据推翻旧决策时 **保留旧记录**，新增版本和变更原因，**不删历史**

**回答格式**（涉及技术选择时）：决策问题 → 候选方案 → 量化数据来源 → 优缺点与风险 →
为什么最适合本项目 → 什么条件下改选 → 如何验证 + 失败回退路径。
