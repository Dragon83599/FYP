# 部署平台候选与筛选（2026-10-29）

> 目的：**不预设 ESP32 或树莓派**，先列全部可行候选，再按需求筛。
> 数据来源标注：**【规格】**= 厂商公开规格；**【实测】**= 文献/我们测过；**【E4】**= 估算，未实测。

## 一、需求清单

### 必须满足（硬门槛）

| # | 需求 | 量化门槛 | 理由 |
| --- | --- | --- | --- |
| M1 | 能采心音 | I2S/ADC + 数字麦克风，采样率 ≥2 kHz | 我们的管线是 2 kHz |

## 四之一、ESP32-S3 vs STM32F405：淘汰 F405 的真实理由（2026-10-30）

> **先撤回一个错误**：此前用"27 实测 1.58 s 跑 1.59M FLOPs → 推算我们 8M MACs 约 8 s"作为淘汰理由。
> 这个外推**不成立**：27 的等效算力约 **0.5 MMAC/s**，比 M4F 峰值（约 168 MMAC/s）低 **约 300 倍**，
> 说明 1.58 s 主要不是卷积耗时（可能含采集或 HSMM 的 Viterbi）。**不能拿它做算力外推。**

| 项 | **ESP32-S3** | **STM32F405** |
| --- | --- | --- |
| 核心/主频 | 双核 LX7 **240 MHz** | 单核 M4F **168 MHz** |
| SRAM | **512 KB** + PSRAM | **192 KB** |
| int8 加速 | **向量指令**（esp-dl）| CMSIS-NN，无 int8 点积硬件 |
| **无线** | **WiFi + BLE5 内置** | **无**，需外挂模块 |
| 我们权重（≈40 kB）后的 SRAM 余量 | 约 **472 kB** | 约 **152 kB** |
| 价格 | ¥30–60 | ¥40–80 |
| PCG 文献先例 | **无** | **有（27）**，但**被迫裁剪模型**、掉 3.8 点 |

**淘汰 F405 的四条理由（替换原来的"算力不足"）**

1. **无内置无线**——需外挂 BLE/WiFi 模块，多一套硬件、驱动、功耗与 PCB 面积；
2. **SRAM 192 KB 不够宽**——27 在此芯片上**被迫删层、调 LSTM**，设备端掉 **3.3–3.8 点**；这与我们 ADR-026（训练前定死结构、不裁剪）正面冲突；
3. **工具链**——我们已有 ESP32-S3 链路与量化经验，换 F405 等于从零开始（M7）；
4. **算力未测**——27 的数字不自洽，**不能作为"跑不动"的证据**；真实耗时待 spike。

**一个可直接讲的加分点**：我们做了**数字自洽性核对**——发现 27 报的 1.58 s 与 1.59M FLOPs 相差约 300 倍于硬件峰值，因此**没有拿它做外推**。这说明我们不是照抄文献数字。

## 四之二、手机 PWA 的实测数字（来自 17，一手）

| 项 | 原文/数字 |
| --- | --- |
| 部署方式 | Keras → **TensorFlow.js** → **PWA（渐进式 Web 应用）**；**不是 APK** |
| 测试设备 | 四种手机，iOS 与 Android 都有 |
| 端上推理 + 微调 | **0.03–0.37 s** |
| 对比：标准 CNN（参数 ×10）| **0.22–5.7 s** |
| 极例 | 大模型在 Samsung Galaxy A30 上 **>5 s**；小模型 **<0.4 s** |
| 技术约束 | TF.js 用 **WebGL** 后端；Android Chrome 的**最大纹理尺寸 4096**，模型/输入过大会失败 |

**对我们意味着什么**

| 优点 | 缺点 |
| --- | --- |
| 零硬件成本、开发最快（PWA 装到桌面即用）| **不满足"低功耗可穿戴"卖点**（手机是现成的）|
| 有**一手实测时延**（0.03–0.37 s），比 MCU 的估算可靠 | 依赖浏览器与 GPU（WebGL），**不同机型差异大** |
| 可作为"参考实现"的第三条轨 | 麦克风质量参差；采样率由手机决定（需重采样到 2 kHz）|

**与 APK 的区别（容易混）**

| | PWA | APK |
| --- | --- | --- |
| 本质 | 网页应用，浏览器内核运行，可"安装"到桌面 | Android 原生安装包 |
| 推理后端 | TensorFlow.js（WebGL/WASM）| TFLite（CPU/NNAPI/GPU delegate）|
| 开发量 | 小（HTML/JS）| 中（Java/Kotlin + 权限 + 打包）|
| 本项目是否需要 | **若走手机轨，优先 PWA**（照 17）| 除非答辩要求"原生 App" |

## 五、建议：先做 spike，再定板

**不要现在拍板**——因为所有时延都是估算。建议 **W3 末做一次 1 天的 spike**：

| 步骤 | 做什么 | 产出 |
| --- | --- | --- |
| 1 | 把 A3 导出 int8（TFLite） | 模型体积、输入输出形状 |
| 2 | 在**树莓派 4B** 上跑 TFLite，测 100 次 | 参考时延（最可能成功）|
| 3 | 在**ESP32-S3** 上跑 esp-dl，测 100 次 | 部署时延（关键未知）|
| 4 | 若 S3 的 RTF >1.2，换 A3-1.5s 模型再测 | 备选方案 |
| 5 | 仍不达标 → 评估 ESP32-P4 / STM32N6 | 决策依据 |

**判断规则**：

- S3 的 RTF ≤1.2 → **S3 为部署轨，RPi 4B 为参考轨**（当前默认）；
- S3 的 RTF 1.2–1.5 → 保留 S3，但论文写"筛查可用、连续监测不可用"；
- S3 的 RTF >1.5 → 换 ESP32-P4 或退到 Zero 2W。

## 七、结论（暂定，待 spike）

**入围 5 项**：ESP32-S3（主）、ESP32-P4（备）、STM32N6（激进）、树莓派 4B（参考）、Android PWA（演示）。

**建议路径**：先用 **RPi 4B 保证"有结果"**，再攻 **S3 拿"端侧"卖点**；P4/N6 只在 S3 不达标时启用。
