## 1. 已确认的产品形态

最终产品采用二体式结构：

- 探头贴胸采集心音，负责传感器、模拟前端、ADC 和探头侧数字处理。
- 主机独立存在，负责接收、显示、回放、边缘 AI 推理和外部通信。
- 主机在没有手机或服务器时，仍能完成采集、显示、回放和初步 AI 判断。

## 2. 已确认的连接关系

系统包含两段明确的外部链路：

```text
无线探头
  -> 无线链路 A：探头与主机，连接方式不限
主机
  -> 蓝牙链路 B：蓝牙连接手机或服务器
手机或服务器
```

### 2.1 探头与主机

- 探头与主机必须使用无线连接。
- 无线连接制式不限定，可以是 BLE、2.4 GHz 私有协议、Wi-Fi 或其他
  可行无线方案。
- 选择无线方案时必须同时满足带宽、延迟、功耗、体积和抗干扰要求。
- 探头必须在无线发送前完成 ADC 采样、组帧、序号、时间戳和 CRC。

### 2.2 主机与外部设备

- 主机必须支持蓝牙。
- 主机可以通过蓝牙直接连接服务器。
- 主机也可以通过蓝牙连接手机。
- 手机可以作为蓝牙网关，再通过蜂窝网络或 Wi-Fi 连接云端服务器。
- 若“服务器”指云端服务器而不是身边的本地服务器，主机直接连接蓝牙
  服务器通常需要一个蓝牙网关或局域网节点。

## 3. 对系统架构的直接影响

- ADC 和数字化必须放在探头内，不能把模拟信号直接无线发送。
- 探头和主机各自需要独立的 MCU 或 SoC、电源和无线模块。
- 探头侧固件负责采集确定性、缓冲和音频帧生成。
- 主机侧固件或应用负责分片重组、显示、回放、边缘 AI 和蓝牙通信。
- 探头到主机的原始音频链路最低需要承载：

```text
320 B PCM / 20 ms = 16.0 kB/s = 128 kbps
352 B frame / 20 ms = 17.6 kB/s = 140.8 kbps
```

以上不包含无线协议开销、重传和链路维护。实际方案应保留至少约 2 倍
吞吐余量，并在真实环境中验证连续传输。

## 5. 仍需继续确认的硬件与产品细节

| 项目 | 需要确认 |
| --- | --- |
| 探头到主机的无线制式 | BLE、2.4 GHz 私有协议、Wi-Fi 或其他方案 |
| 主机蓝牙制式 | BLE、经典蓝牙 SPP 或双模方案 |
| 手机 App 的角色 | 仅显示，还是同时作为上传网关和用户界面 |
| 服务器形态 | 本地服务器、局域网网关还是云端服务 |
| 上传范围 | 原始音频、4 kHz AI 输入、特征、BPM、结果摘要或告警 |
| 上传时机 | 实时流式上传，还是测量结束后按会话批量上传 |
| 探头和主机主控型号 | 分别提供 SRAM、Flash、PSRAM、DMA 和无线能力 |
| 两块电池与充电 | 容量、充电方式、功耗预算和状态指示 |
| 无线共存 | 探头-主机链路与主机-手机/服务器蓝牙链路是否互相干扰 |

## 6. 团队分工：按端划分

当前建议按设备端划分责任，避免探头和主机之间的接口落到灰区。该分工
仍需队友最终确认。

| 责任范围 | 负责人 | 主要工作 |
| --- | --- | --- |
| 探头端 | 队友 | 传感器选型、模拟前端、ADC、探头 MCU、探头无线 TX、探头电源、探头 PCB/结构、探头侧固件。 |
| 主机端 | 本人 | 无线 RX、主机 MCU/SoC、显示、扬声器回放、边缘 AI、本地缓存、蓝牙、主机电源、主机 PCB/结构、GUI。 |
| 链路 A 接口 | 双方共同 | 分片、重组、CRC、丢帧统计、时间戳语义、吞吐和延迟测试。 |
| 系统级集成 | 双方共同 | 探头-主机联调、两段无线共存、端到端验收和最终演示。 |

建议进一步按以下方式切分链路责任：

- 探头侧无线 TX 由队友负责，主机侧无线 RX 由本人负责。
- 双方先共同冻结链路 A 的应用层协议，再各自实现本端。
- 主机蓝牙链路 B 由本人负责，包括手机或服务器连接和上传策略。
- 真实硬件联调时，链路 A 的问题以“谁负责本端、谁提供本端日志”
  为原则定位，协议字段争议回到 `docs/phase0-interface-freeze.md`。

## 7. 当前统一口径

推荐在后续汇报和文档中使用以下表述：

> 项目采用二体式结构。探头通过无线链路连接主机，具体制式不限定。
> 主机通过蓝牙连接手机或服务器；手机可以作为网关连接云端服务器。
> 主机仍可脱离手机和服务器独立完成采集、显示、回放和边缘初步诊断。
> 分工上按设备端划分：队友负责探头端，本人负责主机端，链路 A 协议由
> 双方共同冻结。
