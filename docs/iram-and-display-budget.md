# IRAM / DIRAM 与显示预算分析（2026-10-19）

> 结论先行：**"IRAM 100% 占满"是真的，但它不是加显示/AI 的障碍**。
> 真正的约束是共享 SRAM（DIRAM）的 171 KB 余量，以及显示方案怎么选。
> 本文纠正了 README / 交接文档里"必须先腾 IRAM"的说法。

## 1. 现状（实测）

`idf.py size`（镜像 512,399 B）：

| 区域 | 已用 | 总量 | 余量 |
| --- | ---: | ---: | ---: |
| IRAM（指令专用窗口） | 16,384 | 16,384 | **0（100%）** |
| DIRAM（共享 SRAM） | 169,979 | 341,760 | **171,781** |
| Flash Code | 322,056 | — | 分区余量充足 |
| Flash Data | 86,156 | — | — |

## 2. 为什么"IRAM 100%"不等于没内存

ESP32-S3 的 SRAM 在地址空间里有**两个别名**：

- 指令别名 `0x4037xxxx`（可执行）
- 数据别名 `0x3FC8xxxx`（可读写）

链接脚本里两个区间**大量重叠**：

```text
iram0_0_seg  0x40374000  len 0x57700 = 358,144 B
dram0_0_seg  0x3FC88000  len 0x53700 = 341,760 B
非重叠的指令专用窗口 = 0x57700 - 0x53700 = 0x4000 = 16,384 B
```

`idf.py size` 把重叠部分算进 DIRAM，只把 16,384 B 的非重叠窗口报成 IRAM。
所以"IRAM 100%"只说明**那个 16 KB 的指令专用窗口满了**，不代表 SRAM 用完。

交叉验证（数字完全吻合）：

```text
map 里 .iram0.text                = 86,739 B
size 报的 DIRAM .text 71,383 B
              + IRAM .text 15,356 B = 86,739 B   ✓
```

**真实含义**：新增带 `IRAM_ATTR` 的函数（尤其是 ISR）可能链接失败；
普通代码和数据不受影响，它们用的是那 171 KB 的 DIRAM。

## 3. 真正的预算问题：显示

320×240 RGB565 全帧缓冲 = **153,600 B**。DIRAM 余量 171,781 B，减完只剩 18,181 B，
再放 AI 激活（小 CNN 约 8 KB，TCN 约 31 KB）就非常紧张，且没有余量给栈和堆增长。

### 候选方案

| 方案 | 内存 | 依赖 | 优点 | 缺点 |
| --- | ---: | --- | --- | --- |
| **A. 全帧缓冲放 PSRAM** | DIRAM 仅需小块 | 必须开 `CONFIG_SPIRAM`（N16R8/N8R2 支持） | 刷新逻辑简单、可双缓冲、无撕裂 | PSRAM 读写慢；SPI DMA 从 PSRAM 取数需实测；增加功耗 |
| **B. 不做全帧缓冲，直接画**（推荐） | 行缓冲 320×16×2 = **10,240 B** | 无 | 省内存、不依赖 PSRAM、给 AI 留足余量 | 刷新逻辑复杂；整屏重绘 SPI 流量大 |
| C. 降分辨率（如 240×135） | 64,800 B（全帧） | 无 | 折中 | 显示质量下降，界面信息密度低 |

### 为什么推荐 B

- 本项目的界面是**波形 + 分数 + 心率**，不是动画/图片，天然适合增量绘制（只重画波形条）；
- 不需要改 `sdkconfig`，不引入 PSRAM 的 DMA/功耗风险；
- DIRAM 余量保持在 160 KB 以上，AI 与协议栈都宽松。

SPI 带宽估算：320×240×2 = 153,600 B/帧；40 MHz SPI 理论 5 MB/s，
整屏刷新约 31 ms（≈32 fps 上限），实际按 10–15 fps 设计足够。

## 4. 如果确实需要 16 KB 指令窗口

只有当显示驱动或 AI 前端**必须**用 `IRAM_ATTR` ISR 时才需要腾。可选动作（按代价排序）：

1. 关掉不用的 IRAM 选项：`CONFIG_I2C_MASTER_ISR_HANDLER_IN_IRAM`（本项目暂时无 I2C 从设备需求时）、`CONFIG_GPTIMER_ISR_HANDLER_IN_IRAM`；
2. 把非热路径的 `IRAM_ATTR` 函数改回 flash；
3. 用 SPI 驱动自带的 ISR（ESP-IDF 的 `spi_master` 已在 flash 运行，不需要额外 IRAM）。

上述任一项都能腾出几 KB，且不影响功能。

## 5. 验证方法（板子到货后）

| # | 验证 | 判据 |
| --- | --- | --- |
| 1 | 开/不开 PSRAM 各构建一次 | `idf.py size` 中 DIRAM 余量 ≥ 60 KB |
| 2 | 显示整屏刷新 | ≥10 fps，无明显撕裂 |
| 3 | 波形增量刷新 | 只重画波形区，CPU 占用可测 |
| 4 | 加入 INT8 推理后 | 峰值堆余量 ≥ 40 KB，单窗推理 < 200 ms |
| 5 | 5 分钟连续运行 | 无内存泄漏（堆曲线平稳） |

## 6. 对既有文档的更正

README、`docs/handoff-2026-10-19.md`、`docs/implementation-roadmap.md` 里
"IRAM 100% 占满，必须先腾 IRAM"的说法**不准确**，已改为：
"16 KB 指令专用窗口已满（只影响 `IRAM_ATTR`/ISR 的新增）；真实预算是 DIRAM 余量 171 KB"。

## 7. 证据等级

- IRAM/DIRAM 数字：本机 `idf.py size` 与 ELF 段表实测（E4，可复现）
- 链接区间与别名关系：ESP-IDF 链接脚本（一手）
- SPI 刷新率：按 40 MHz 理论带宽估算（E4），**必须上板实测**
- PSRAM 的 SPI DMA 可用性：未验证，标为风险
