# 蓝牙名词：零基础版

> 用法：答辩前只需要真正讲清楚**第 1 节的 6 个词**；其余知道是什么即可。
> 每个词都给"一句话版"和"类比"。

## 1. 必须会讲的 6 个（答辩会被问）

### 1.1 BLE（低功耗蓝牙）

- **一句话**：一种"每隔一会儿快速说几句"的无线通信方式，专门为省电设计。
- **类比**：对讲机，不是打电话。打电话要一直连着；对讲机是"喂，收到吗"说一句就停。
- **为什么用它**：探头是电池供电，BLE 比经典蓝牙省电得多。

### 1.2 Central / Peripheral（中心 / 外设）

- **一句话**：外设负责"开门等客"，中心负责"主动找店"。
- **类比**：探头是店铺（挂招牌等客），主机是顾客（主动进店）。
- **本项目**：探头 = 外设，主机 = 中心。
- **为什么重要**：谁主动，决定了连接参数由谁提。

### 1.3 GATT（通用属性协议）

- **一句话**：蓝牙设备之间"有什么可以给你"的清单格式。
- **类比**：店里的菜单。菜单分"大类"（服务）和"具体菜品"（特征）。
- **本项目**：菜单上有一项"音频服务"，下面有三道菜：音频数据、控制、状态。

### 1.4 Characteristic（特征）

- **一句话**：GATT 菜单里的一道菜，是真正传数据的地方。
- **类比**：每道菜有名字（UUID）、有规矩（能不能读/写）、有货架号（handle）。
- **本项目**：三个特征——音频数据（探头→主机）、控制（主机→探头）、状态（探头→主机）。

### 1.5 Notify（通知）

- **一句话**：店家主动上菜，不等你问，也不管你收没收到。
- **类比**：食堂阿姨把菜往你桌上一放就走。
- **为什么用它**：音频流每秒要送 100 包，等确认太慢。
- **反面对比**：Indicate 是"上菜要你签字"，保证送到但一次只能送一道，太慢。

### 1.6 MTU（最大传输单元）

- **一句话**：一次能装多少字节。
- **类比**：盘子大小。盘子越大，端的次数越少。
- **本项目**：MTU 247 → 一次能装 244 B 数据。
- **为什么重要**：352 B 的音频帧，盘子够大就分 2 次端，盘子小就要分 3 次。

## 2. 知道就行的词

| 名词 | 一句话 | 类比 / 本项目取值 |
| --- | --- | --- |
| 广播（Advertising） | 探头周期性地喊"我在这里" | 店铺挂招牌 |
| 扫描（Scanning） | 主机到处找招牌 | 顾客在街上逛 |
| 连接（Connection） | 主机连上探头，约定通信节奏 | 进店点菜 |
| 服务（Service） | GATT 菜单里的大类 | "音频服务" |
| UUID | 每个服务/特征的编号 | 门牌号，两端必须一致 |
| Handle | 特征的内部货架号 | 客户端拿到后按号取货 |
| CCCD | 一个"订阅开关"，打开后才会收到通知 | 你说"这道菜我要"，厨房才开始送 |
| Write（写） | 主机把指令写到探头 | 点菜 |
| Indicate | 需要对方确认的通知 | 上菜要签字（太慢，不用） |
| 连接间隔 | 两次通信之间隔多久 | 每 15 ms 送一次菜 |
| 连接事件 | 一次通信机会里可以连送几包 | 一次上菜可以端两盘 |
| PHY（1M / 2M） | 无线传输的速度档位 | 1 米/秒 或 2 米/秒 |
| DLE（数据长度扩展） | 允许一次装更多（251 B） | 允许用大盘子；没有它一盘只能装 27 B |
| 分片 | 一份数据装不下，拆成几份 | 一盘装不下分两盘 |
| 配对（Pairing） | 第一次见面交换信物 | 加微信好友 |
| 绑定（Bonding） | 把信物存下来，下次免认证 | 记住好友，下次直接说话 |
| Just Works | 不问密码直接配对 | 谁敲门都开（方便但不防冒充） |
| Passkey | 要输入 6 位暗号才配对 | 对暗号 |
| OOB | 通过别的渠道给暗号 | 扫码加好友 |
| 中间人攻击 | 有人冒充店家在中间转话 | 你以为是真店，其实是二道贩子 |
| kbps | 每秒传多少千位 | 140.8 kbps ≈ 每秒 17.6 KB |
| PCM | 最原始的录音数据格式 | 每个采样点存一个数字，不压缩 |
| ADPCM | 一种压缩格式（约 4:1） | 把 4 个数字压成 1 个，有损失 |
| LC3 | 蓝牙为语音设计的压缩格式 | 为"人说话"优化，心音不适用 |
| L2CAP CoC | 绕过 GATT 直接传数据的通道 | 后门直送，快但复杂 |
| LE Audio | 蓝牙组织为耳机/助听器定的新音频标准 | 需要专门的硬件支持 |
| ESP-NOW | 乐鑫自己的无线传输方式，不是标准蓝牙 | 自家对讲机，只有乐鑫芯片能用 |
| NimBLE | 乐鑫的开源蓝牙协议栈 | 我们用的"蓝牙实现" |
| ESP-IDF | 乐鑫的固件开发框架 | 写固件用的工具包 |
| P95 延迟 | 95% 的包能在这个时间内到达 | 比平均值更能反映"卡不卡" |
| 丢帧率 | 100 帧里丢了几帧 | 本项目要求 ≤0.1% |
| 占空比 | 一段时间里真正在传数据的比例 | 本项目约 28% |
| 环形缓冲 | 一个"先进先出"的临时存储 | 数据先排队，慢慢处理 |

## 3. 把整件事连起来讲一遍（30 秒版）

> 探头是店铺，它一直在广播（挂招牌）。
> 主机是顾客，扫描到招牌后连上去。
> 连上以后双方先谈"盘子多大"（MTU 247），再谈"传多快"（2M PHY），
> 然后主机说"这道菜我要"（打开 CCCD）。
> 之后探头每 20 毫秒把 352 字节的心音数据拆成两盘端过来（Notify），
> 主机每 15 毫秒接一次（连接间隔）。
> 主机想让它开始/停止，就点菜（Write 到控制特征）。
> 第一次见面要配对，之后靠绑定免认证。

## 4. 答辩时怎么用

- 被问"蓝牙怎么传数据的" → 讲第 3 节的 30 秒版，加上"每秒 100 个包、140.8 kbps、占空 28%"。
- 被问"为什么不用 Wi-Fi/经典蓝牙" → 功耗：探头是电池供电，BLE 最省。
- 被问"为什么不用 LE Audio" → 需要专门硬件（ISO 通道），我们的芯片不支持，而且我们的带宽本来就用不完。
- 被问"安不安全" → Just Works 不防中间人；如果要更高安全，要给探头加按键升级 Passkey。

## 5. 记住三句话就够了

1. **探头等，主机找**（Peripheral / Central）。
2. **菜单是 GATT，上菜是 Notify，点菜是 Write**。
3. **盘子越大端得越少**（MTU 247 → 2 包一帧；若只有 158 → 3 包）。
