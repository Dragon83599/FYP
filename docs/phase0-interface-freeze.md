# 阶段 0：数据与硬件接口冻结记录

> 状态：产品形态与两段无线链路已确认，器件与无线制式待确认
>
> 基线版本：v0.2
>
> 更新日期：2026-10-07
>
> 冻结规则：确认后只能通过版本号升级修改；任何一侧不得私自在字段、单位、字节序或时间语义上做兼容性之外的变化。

## 1. 本阶段目标

阶段 0 不是把功能全部实现，而是形成一份双方可以共同验收的接口合同。完成后应能回答：

1. 传感器输出什么信号，有效带宽是多少。
2. 探头内的 ADC 如何把信号交给探头 MCU，数据是否可能丢样。
3. 探头以什么采样率、帧长、数据类型和时间信息通过无线链路发送数据。
4. 主机如何判断帧边界、顺序、时间戳和损坏。
5. 探头主控和主机主控的 RAM/Flash 是否足以容纳采集、协议、显示、
   无线协议栈和推理模型。
6. 探头无线模块、主机蓝牙模块、屏幕和 ADC 是否争用同一通信接口。
7. 探头到主机链路和主机到手机/服务器链路如何共存并满足吞吐、延迟和
   丢帧要求。

## 3. 采样率决策

有效带宽为 `20~1000 Hz`：

- 理论最小采样率：大于 `2 x 1000 = 2000 Hz`。
- 只做心音 AI 的最低工程值：`4000 Hz`。
- 兼顾抗混叠、时间分辨率和后续算法：推荐 `8000 Hz`。
- 只有产品明确要求自然人声、环境声或宽带录音时，才考虑 `16000 Hz`。
- `44.1/48 kHz` 对 20~1k 心音没有额外医学信息，反而增加带宽、存储、功耗和缓冲压力。

推荐数据处理链：

```text
[probe]
sensor -> analog anti-alias -> ADC -> 8 kHz 16-bit capture
       -> probe MCU buffering and 20 ms frame packing
       -> wireless link A (method TBD)

[host]
wireless link A -> de-frame and CRC check
                |-> 8 kHz record / speaker playback
                `-> anti-alias -> decimate by 2
                                  `-> 4 kHz edge AI input

[external]
host -> Bluetooth link B -> phone or server
```

如果探头最终只采 4 kHz，则必须确认探头模拟前端在 2 kHz 前已经充分衰减；
否则 1~2 kHz 的干扰会混叠到 0~1 kHz。不能一边采 4 kHz，一边把原始数组
直接传入需要 8 kHz 或 16 kHz 的模型。

```text
link A minimum application throughput:
  320 B PCM per 20 ms  = 16.0 kB/s = 128.0 kbps
  352 B frame per 20 ms = 17.6 kB/s = 140.8 kbps
```

以上数值不包含无线协议开销、重传和链路维护。探头-主机无线方案应至少
按约 2 倍余量选型，并在真实环境验证连续传输。

## 4. 帧和缓冲定义

| 项目 | 8 kHz 基线 | 16 kHz 条件分支 |
| --- | ---: | ---: |
| 每帧时长 | 20 ms | 20 ms |
| 每声道样本数 | 160 | 320 |
| PCM 负载 | 320 B | 640 B |
| 协议头 | 30 B | 30 B |
| CRC | 2 B | 2 B |
| 单帧完整长度 | 352 B | 672 B |

`AUDIO_FRAME_SIZE` 统一表示“每声道样本数”，不要表示整个数组的字节数。完整负载字节数按以下公式计算：

```text
payload_bytes = frame_samples * channel_count * 2
frame_bytes   = 30 + payload_bytes + 2
```

探头-主机链路无论采用 BLE、2.4 GHz 私有协议、Wi-Fi 还是其他无线方案，
都必须允许传输层分片或等价的大包传输机制。应用层仍以完整 20 ms 帧为
CRC 和 AI 推理单位。若所选无线方案只能发送很小的单包，才考虑把逻辑帧
改为 10 ms，并同步修改所有文档和代码。

建议 RAM 预算。探头和主机必须分别核算，不能把两者的剩余资源混在一起：

| 用途 | 8 kHz, 20 ms | 16 kHz, 20 ms |
| --- | ---: | ---: |
| DMA 双缓冲 | 640 B | 1280 B |
| 8 帧待发送环形队列 | 2560 B | 5120 B |
| 编解码/栈/对齐余量 | 约 1 KB | 约 2 KB |
| 探头采集、无线与协议小计 | 约 6 KB | 约 12 KB |

以上不包含探头无线协议栈、主机屏幕 framebuffer、主机蓝牙协议栈、
文件系统和 AI 模型。探头和主机主控选型均应至少保留 30% 峰值 RAM 余量。

## 5. 数据语义

### 5.1 `int16_t` PCM

- 有符号、16-bit、小端。
- 满量程范围：`-32768` 到 `32767`。
- ADC 若为无符号 12-bit，推荐按 `(int16_t)((raw - 2048) << 4)` 转换为有符号 16-bit；若 ADC 已经输出有符号 12-bit，则直接左移 4 位。
- 增益、校准和滤波必须在协议中保持可追踪；不要一侧发送原始 ADC 码，另一侧却假设已经归一化。
- 降噪、带通、抽取等修改数据的处理必须在探头 DSP、主机 DSP 或主机
  软件中明确指定执行位置，避免两端重复处理或改变数据语义。

### 5.2 时间戳

- 单位固定为毫秒，不发送浮点秒。
- 表示第一个有效样本被采集的时间。
- 连续帧理论间隔为 20 ms；使用样本计数生成时间戳，比在每个 DMA 回调里读取系统毫秒更稳定。
- 无线发送抖动不应写入时间戳。

### 5.3 序列号和声道

- `sequence` 每帧递增 1，`uint32_t` 自然回绕。
- `channel_count = 1`，每个样本先是 channel 0，再进入下一采样时刻。
- 若以后变为双通道，必须升级协议版本并规定交错顺序，不能只改数值。

## 6. 固定线格式

协议使用固定小端字段，不直接发送带编译器 padding 的 C 结构体。完整格式如下：

| 偏移 | 长度 | 字段 | 类型 | 说明 |
| ---: | ---: | --- | --- | --- |
| 0 | 4 | `magic` | ASCII `AUD1` | 固定值，用于同步和版本识别 |
| 4 | 1 | `version` | `uint8_t` | 当前为 `1` |
| 5 | 1 | `flags` | `uint8_t` | bit0 表示 timestamp 有效 |
| 6 | 2 | `header_bytes` | `uint16_t` | 固定为 `30` |
| 8 | 1 | `codec` | `uint8_t` | `1 = PCM_S16_LE` |
| 9 | 1 | `channels` | `uint8_t` | 当前为 `1` |
| 10 | 1 | `bits_per_sample` | `uint8_t` | 固定为 `16` |
| 11 | 1 | `reserved` | `uint8_t` | 发送时必须为 `0` |
| 12 | 4 | `sample_rate_hz` | `uint32_t` | 当前为 `8000` |
| 16 | 4 | `frame_samples` | `uint32_t` | 当前为 `160`，每声道样本数 |
| 20 | 4 | `sequence` | `uint32_t` | 帧序号 |
| 24 | 4 | `timestamp_ms` | `uint32_t` | 首样本采集时刻 |
| 28 | 2 | `payload_bytes` | `uint16_t` | 当前为 `320` |
| 30 | N | `payload` | bytes | `int16_t` PCM，小端交错 |
| 30+N | 2 | `crc16` | `uint16_t` | 对 header 和 payload 计算，小端 |

CRC16 建议冻结为 `CRC-16/CCITT-FALSE`：

```text
poly   = 0x1021
init   = 0xFFFF
refin  = false
refout = false
xorout = 0x0000
```

双方必须对同一个已知帧得到相同 CRC，否则接口尚未真正冻结。

### 6.1 固定测试向量

测试输入：

| 字段 | 值 |
| --- | --- |
| `version` | `1` |
| `flags` | `0x01` |
| `header_bytes` | `30` |
| `codec` | `1` |
| `channels` | `1` |
| `bits_per_sample` | `16` |
| `sample_rate_hz` | `8000` |
| `frame_samples` | `160` |
| `sequence` | `1` |
| `timestamp_ms` | `1000` |
| `payload_bytes` | `320` |
| payload | 160 个 `int16_t` 零样本，共 320 个 `0x00` 字节 |

期望 header 的十六进制字节：

```text
41 55 44 31 01 01 1E 00 01 01 10 00
40 1F 00 00 A0 00 00 00 01 00 00 00
E8 03 00 00 40 01
```

对 header + 320 个零 payload 计算 `CRC-16/CCITT-FALSE`：

```text
crc16          = 0x7B5E
wire crc bytes = 5E 7B
full frame     = 30 B header + 320 B zero payload + 2 B CRC
```

## 7. 主控和通信接口约束

### 7.1 探头与主机的最低能力

在选型表填写准确型号前，至少分别验证：

探头侧：

- SRAM：ADC/DMA 双缓冲、帧缓冲、无线协议栈、重传队列和峰值栈。
- Flash：固件、升级分区、设备参数和必要的采集缓存。
- DMA：ADC/I2S/SPI 至少有一条可稳定搬运连续音频。
- 时钟：采样率误差应在可接受范围内；晶振或 I2S 主时钟优先于粗糙软件延时。
- 中断：音频 DMA 中断不能被无线发送长时间阻塞，也不得长时间关闭全局中断。

主机侧：

- SRAM/PSRAM：无线接收重组、显示 framebuffer、扬声器回放缓冲、
  蓝牙协议栈、边缘 AI 模型及峰值工作区。
- Flash：固件、UI 资源、模型、本地缓存和双分区升级空间。
- DMA/外设：显示刷新、音频回放和蓝牙至少不能互相造成长时间阻塞。
- CPU/NPU：边缘 AI 推理延迟和功耗必须满足实时显示与回放要求。

探头和主机均应至少保留 30% 峰值 RAM 余量。

### 7.2 探头内 ADC 到探头 MCU

候选方案按优先级：

1. 模拟传感器：MCU 内 ADC + timer trigger + circular DMA + half/full callback。
2. 数字 MEMS：I2S 或 PDM，核对麦克风低频截止和 DC 处理。
3. 外置 ADC：SPI/I2S，使用 DRDY 或固定采样时钟；若使用 SPI，必须确认吞吐率。

禁止使用逐样本阻塞读取。每帧处理函数只消费已经完整写入的 buffer，不直接读正在被 DMA 写入的区域。

### 7.3 主机屏幕、蓝牙和无线共享通信接口

- 最优先方案是屏幕和无线模块使用不同总线。
- 若必须共享 SPI，则屏幕和无线各自使用独立 CS。
- 建立单一总线所有权锁，禁止任务在执行事务时被抢占后交叉访问。
- 主机蓝牙收发突发不能阻塞探头音频接收、DMA 音频搬运和扬声器回放。
- 探头无线发送不能阻塞 ADC 采集和下一帧的确定性组帧。
- 记录共享总线的最高稳定时钟、DMA 使用情况和最大阻塞时间。
- 不要把 ADC 放在屏幕/无线共享总线上。

### 7.4 两段无线链路约束

链路 A：探头到主机。

- 应用层最低吞吐约 `140.8 kbps`，即 `352 B / 20 ms`。
- 实际无线方案建议至少提供约 2 倍应用层余量，以覆盖协议开销、重传、
  连接维护和同频干扰。
- 必须定义分片、重组、分片序号、CRC 和丢帧统计。
- 探头生成 `sequence` 和 `timestamp_ms`；主机不得重新生成或覆盖。
- 建议第一版把采集到主机显示或回放的端到端缓冲目标控制在 300 ms
  以内，最终指标由产品形态和 AI 模型窗口决定。

链路 B：主机到手机或服务器。

- 主机必须支持蓝牙连接手机或服务器。
- 需要明确使用 BLE GATT、经典蓝牙 SPP 还是双模方案，以及对应 MTU、
  连接间隔、吞吐和配对方式。
- 如果链路 B 需要原始 8 kHz PCM，则同样需要约 `140.8 kbps` 的持续
  吞吐；如果只上传 BPM、特征或 AI 结果，吞吐要求会显著降低。
- 如果服务器是远端云端且主机没有网络接口，应由手机作为网关转发，
  或增加本地蓝牙网关。
- 链路 B 断开不得影响主机的采集、显示、回放和边缘 AI。

共存要求：

- 链路 A 和链路 B 必须能同时工作。
- 需要在真实环境测试两段链路的相互干扰、吞吐下降、重传和延迟峰值。
- 任何一段链路重连时，另一段链路和本地显示/回放不得出现长时间卡顿。

## 8. 完成阶段 0 的证据

双方确认以下内容后，才把状态改为“已冻结”：

- [ ] 准确填写探头主控和主机主控的型号、RAM、Flash、PSRAM 和可用 DMA。
- [ ] 确认传感器型号及 20 Hz、1 kHz 附近的实测或 datasheet 响应。
- [ ] 确认探头内模拟前端、ADC 位数、参考电压、增益和抗混叠方案。
- [ ] 双方使用同一份 `shared/include/audio_protocol.h`。
- [ ] 用固定测试帧生成相同 header 字节和 CRC。
- [ ] 输入 20 Hz、100 Hz、440 Hz、1 kHz 正弦波，验证频率和幅值。
- [ ] 连续采集并经过探头-主机无线链路传输至少 5 分钟，确认无 DMA
      overrun、丢帧、重传堆积和内存增长。
- [ ] 记录链路 A 的实际吞吐、平均延迟、P95 延迟和最大延迟。
- [ ] 主机同时连接探头和手机/服务器时，两段无线链路可稳定共存。
- [ ] 记录链路 B 的蓝牙制式、MTU、连接间隔、吞吐和重连时间。
- [ ] 断开链路 B 后，主机仍能完成采集、显示、回放和边缘 AI。
- [ ] 人为破坏 1 个 payload 字节，接收端必须因 CRC 拒绝该帧。
- [ ] 检查序号跳变时，接收端能报告丢帧；时间戳不得因无线抖动跳变。
- [ ] 文件保存格式明确采样率、位深、声道数、字节序和帧长。
- [ ] 主机屏幕/蓝牙/探头接收的总线方案有明确仲裁规则和实测最大阻塞时间。
- [ ] 用探头和主机最终固件分别生成 map/size 报告，记录静态 RAM、
      Flash 和峰值栈。

## 9. 发给队友的确认消息

```text
组会已确认：探头与主机必须无线连接，主机通过蓝牙连接手机或服务器。
阶段 0 v0.2 在这个前提下继续收敛，请逐项回复“同意/改成什么”：

1. 产品形态为二体式：无线探头负责采集和组帧，主机负责接收、显示、
   回放、边缘 AI 和外部通信。
2. 建议按设备端分工：队友负责探头端，本人负责主机端；探头侧无线 TX

   是否至少保留约 2 倍余量？

   云端，请确认手机或本地网关的角色。

   带限抽取到 4 kHz。
8. 逻辑帧 20 ms，8 kHz 时为 160 samples/channel，PCM 320 B；协议头
   30 B，CRC-16/CCITT-FALSE。
9. 请分别给出探头主控和主机主控的型号、SRAM/Flash/PSRAM、DMA、
   无线能力和功耗预算。
10. 请确认探头 ADC 到探头 MCU 的路径、增益和抗混叠方案，以及主机屏幕、
   蓝牙和探头接收是否共享总线。

20 Hz 附近的频响和低频截止。
```

## 10. 当前未决项

以下项不能由软件端自行假设，必须由硬件负责人给出最终值：

| 未决项 | 为什么阻塞 | 需要队友提供 |
| --- | --- | --- |
| 传感器型号 | 决定低频响应、模拟前端和噪声底 | 型号、datasheet、20~1000 Hz 频响 |
| 探头-主机无线制式 | 决定链路 A 的吞吐、延迟、功耗和抗干扰 | 芯片/模块型号、频段、协议栈、吞吐和实测延迟 |
| 主机蓝牙方案 | 决定链路 B 能否连接手机和服务器 | BLE/SPP/双模、MTU、连接间隔、吞吐和重连时间 |
