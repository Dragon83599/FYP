## 3. 原文没给、由原文数字反推出来的（DERIVED）

### 3.1 卷积的 `padding` 必须是 `same`

原文没写 padding。用原文自己给的 20,193 反推：

| padding | 各层长度（2000 → 池化 → …） | Flatten 后 | FC 参数 | **总参数** |
| --- | --- | ---: | ---: | ---: |
| `valid` | 1981 → 495 → 476 → 119 → 100 → **25** | 100 | 12,928 | **17,121** |
| **`same`** | 2000 → 500 → 500 → 125 → 125 → **31** | **124** | **16,000** | **20,193** ✅ |

卷积本身 336 + 2,568 + 644 = 3,548，输出层 645，两种 padding 相同；差 3,072 全部来自 FC 输入维度（124 vs 100）。
**只有 `same` 能对上 20,193**，所以这不是偏好问题，是原文数字唯一确定的解。
（`tests/python/test_repro_ma2023.py` 把 20,193 与 17,121 都钉住了。）

### 3.2 每条录音只切出 **1 个** 2 s 片段 → 窗数 = 1,000

原文："long and zero-padded short recordings were cropped to make all samples have an exact length of 2 s"。
本地实测录音长度 **1.16–3.99 s（中位 2.43 s）**，按"裁/补到正好 2 s"的规则，**每条录音恰好 1 个片段**：

| 类别 | n | 最短 | 中位 | 最长 | 短于 2 s（需补零） |
| --- | ---: | ---: | ---: | ---: | ---: |
| N | 200 | 2.03 s | 2.41 s | 3.01 s | 0 |
| AS | 200 | 2.35 s | 2.63 s | 3.55 s | 0 |
| MS | 200 | 1.16 s | 2.28 s | 3.20 s | 14 |
| MR | 200 | 1.58 s | 2.22 s | 3.03 s | 16 |
| MVP | 200 | 1.73 s | 2.56 s | 3.99 s | 19 |
| **合计** | **1,000** | | | | **49（4.9%）** |

950 条被裁、49 条被补零、1 条正好 2 s。

**这直接回答了文献笔记里的一个"待查证"**：原文的切窗数不是未知量，就是 **1,000**；
而且因为**每条录音只有一个片段**，原文那个"随机 10 折"**本身就是录音不交叉的**——
笔记里担心的"同一录音的两个窗分到不同折"在**原文的口径下不存在**。

> 结论（重要）：**"随机折 → 录音分组折会掉 1–3 点"这个预期，在 A3-repro 上不成立**。
> 它会掉点只可能来自**我们自己的预处理差异**（2 kHz、带通、z-score、1 s 步进），
> 不会来自分组。W2 若看到落差，查预处理，不要怪划分。

## 9. 实测结果（2026-11-04）

### 9.1 两种停止规则各跑一次 10 折

| 协议 | 10 折均值 | 折间 std | 折间 CI95 | Δ vs 98.65 | 判定（±1.5）|
| --- | ---: | ---: | --- | ---: | --- |
| 早停（内部 10% dev，patience 10） | **97.40%** | 2.01 | 95.96–98.84 | −1.25 pt | 通过（贴边）|
| **固定 100 epoch（不早停）** | **98.60%** | 1.26 | 97.70–99.50 | **−0.05 pt** | **通过** |

逐折（固定 100 epoch）：98 / 100 / 100 / 98 / 100 / 99 / 99 / 98 / 96 / 98。
逐折（早停）：95 / 99 / 98 / 97 / 98 / 99 / 97 / 99 / 93 / 99，epoch 数 24 / 58 / 64 / 32 / 36 / 47 / 36 / 100 / 58 / 100。

**两组差的不是模型，是停止规则。** 早停那组 fold 0 在第 **24** 个 epoch 就停了（最佳 14），
同一折固定训 100 轮是 **98%**。原因是早停用的 dev 只有 **90 条**（训练折的 10%），
验证损失噪声大，容易在还没收敛时触发。原文**没有写停止规则**（只给了"100 epochs 内"的曲线），
所以两种都算合规实现，**两个数都要报**，不能只挑 98.60。

**与原文 CI 不可直接比**：原文 98.555–98.745 是 **40 次 attempt 之间**的 CI（每次 attempt = 一次完整 10 折），
上面报的是**折间** CI。为此又跑了 2 次不同种子的完整 attempt（见 §9.1b）。

### 9.1a 主指标是 macro F1，不是 accuracy（ADR-053）

**从本轮起，判断模型好坏一律看 macro F1**（每类各算 F1 再平均，每类等权）；accuracy 只保留一个用途：**与原文 98.65% 对齐**，因为原文只报了 accuracy，拿 F1 去减 accuracy 是减法错误。

| 指标 | 用途 | 为什么 |
| --- | --- | --- |
| **macro F1** | **主指标**：模型好坏、W3 改进判定 | 每类等权，少数类被漏会被惩罚；本项目窗数最大/最小 1.31×、若换 CirCor 会到 3.7:1，accuracy 会失真 |
| accuracy | **只对文对齐**：与 98.65% 相减 | 原文唯一的报告口径；不做模型好坏判据 |
| 逐类 F1 + 混淆矩阵 | 误差分析 | 说明"错在哪两类之间"，比一个总分有用 |

**这次两组数字几乎相同，是数据决定的，不是巧合**：5 类各 200 条完全均衡，且模型几乎不混，所以 macro F1 ≈ accuracy（98.60 vs 98.60）。换成不均衡数据或加噪扰动，两者会分开——那时 F1 才是能反映问题的那个。

### 9.1b 四次 attempt（同协议，不同初始化）

前三次在加入确定性种子之前跑（初始化随机，对应原文"40 次 attempt"的口径）；
第四次是加入种子后的复算验证跑（§9.5），同样是完整 10 折，故一并计入 attempt。

| attempt | **macro F1（主指标）** | accuracy（仅对文）| 折间 std | Δ vs 98.65 |
| --- | ---: | ---: | ---: | ---: |
| #1 seed 42（未固定种子） | **98.60%** | 98.60% | 1.26 | −0.05 |
| #2 seed 1042（未固定种子） | **98.10%** | 98.10% | 1.79 | −0.55 |
| #3 seed 2042（未固定种子） | **98.30%** | 98.30% | 1.42 | −0.35 |
| #4 seed 42（**固定种子**，复算验证） | **98.60%** | 98.60% | 1.17 | −0.05 |
| **attempt 均值（n=4）** | **98.40%** | 98.40% | 0.25 | **−0.25 pt** |

**F1 是怎么算的**：把 10 折的**折外预测**拼起来（每条录音恰好被预测一次，共 1,000 条），
**先把混淆矩阵求和，再算一次 F1**——不是"每折算一次 F1 再平均"。后者会让某个类在某一折里样本很少时被过度加权，
结果随折划分漂移。

**逐类 F1（#1 的 pooled 结果）与混淆矩阵**（行=真实，列=判读）：

| 类 | F1 | 说明 |
| --- | ---: | --- |
| N | **100.00** | 200/200 全对 |
| MS | 99.00 | 1 条 → MVP |
| AS | 98.51 | 1 条 → MR |
| MVP | 97.98 | 2→AS、1→MS、3→MR |
| MR | **97.49** | 3→AS、2→MS、1→MVP |

```
       AS   MS   MR  MVP    N
AS    199    0    1    0    0
MS      0  199    0    1    0
MR      3    2  194    1    0
MVP     2    1    3  194    0
N       0    0    0    0  200
```

**最弱的是 MR 与 MVP，混淆集中在 MR↔MVP 与 MVP→AS**——这与原文 Fig. 7 的结论一致
（原文扰动条件下也是最弱 MR 0.932、MVP 0.962，混淆集中在 MR↔MVP、MS↔MVP）。
**两套独立数据给出同一个弱点，说明这不是我们实现的偏差**，而是这几类的信号本身接近；
这也是 W3 的 I3（S1 对齐）和 I4（换表示）要攻的点。

attempt 间 95% CI（t 分布，n = 4）：**[98.01%, 98.79%]**，半宽 **0.39 pt**。

**怎么读这个区间**：
- **原文的 98.555–98.745 完整落在我们的 CI 内** → 以现有数据**无法判定两者有差异**；
  点估计低 **0.25 点**，远小于 ±1.5 点的验收门。
- 区间仍比原文宽 **4 倍**（0.39 vs 0.09 pt），因为 **n = 4** 而原文是 **40 次**。
  论文里如实写"4 次 attempt，attempt 间 CI 半宽 0.39 pt"，**不要**假装有原文的精度。
- 若只用前三次（n=3）：均值 98.33%、CI [97.71, 98.96]（半宽 0.63）——两种口径结论一致，都是"无法判定不同"。
- **验收门用点估计**：98.40% 与 98.65% 差 0.25 点，落在 ±1.5 点内 → **通过**。

### 9.3 浏览器一致性（判据 <1e-3）

导出产物：`model.json` **6,603 B** + `group1-shard1of1.bin` **80,772 B**（= 20,193 × 4 B），
用**真的 `@tensorflow/tfjs` 4.22.0**（CPU 后端，与浏览器同一个 `tf.loadLayersModel` 代码路径）加载：

| 检查 | 内容 | 最大绝对差 | 结果 |
| --- | --- | ---: | --- |
| 模型（同一张量） | Python 预处理后的 2,000 点直接喂两边 | **1.19e-7** | 通过 |
| **端到端（同一 wav）** | 浏览器自己读 wav → 重采样 → 裁/补 → min-max → 推理 | **1.19e-7** | 通过 |
| 预处理样本级 | 两边 2,000 点逐点比 | **0**（float32 完全相同） | — |

端到端能到 0 样本差，是因为 JS 侧**复用了 scipy 自己设计的那组 FIR**（`pwa/filters/resample-poly.js`，
由 `tools/ai/make_pwa_filters.py` 生成并在真实录音上与 scipy 对到 **8.9e-16**），
再按 scipy 的"先卷积 → 再抽取 → 再去掉前 11 点"顺序实现，而不是自己另设计一个重采样器。

**真机实测（2026-11-04，安卓 Edge，WebGL 后端）**：

| 项 | 值 |
| --- | --- |
| 设备/浏览器 | Android 10 · Edge `EdgA/156.0.0.0` |
| 后端 | **webgl**（不是回落的 cpu）|
| 模型（同一张量）最大差 | **1.88e-12** |
| 端到端（同一 wav）最大差 | **1.88e-12** |

**这里要专门说一句**：概率差只有 1e-12，看着比 Node 的 1.19e-7 还"准"，但这不是精度更高——
是**模型在这条 AS 录音上饱和了**（AS ≈ 0.999999，其余都在 1e-7 量级），差别被压在极小的数上。
所以**真正有分辨力的是样本级差 = 0**：那说明浏览器的重采样/裁剪/min-max 与 Python 逐点相同，
这才是"同一条路"的证据。只看概率差会被饱和掩盖——我们最初就是靠样本级差抓到了 77 点抽取偏移那个 bug。

**同一个地址在不同浏览器上的结论不同**（值得写进论文的"部署边界"）：

| 浏览器 | 结果 |
| --- | --- |
| 安卓 **Edge** | ✅ 正常，后端 webgl |
| 华为自带浏览器 / 夸克 | ❌ 一直"模型加载中"：接受 `<script type="module">`、文件也下载了，但**不执行模块脚本** |

所以页面对"不支持 ES module 的浏览器"现在会直接提示换 Chrome/Edge/Safari，而不是空等（见 `pwa/README.md` §5）。

### 9.4 端上时延（W2 验收门：中位 ≤1 s、P95 ≤2 s）

同一台安卓 Edge、WebGL 后端，预热 1 次后连跑 **20 次**纯推理（不含预处理与文件读取）：

| 统计量 | 实测 |
| --- | --- |
| 中位 | **4.4 ms** |
| P95 | **5.1 ms** |
| 最小 / 最大 | 3.8 / 6.3 ms |
| RTF（推理时间 ÷ 2 s 窗长）| **0.0022** |
| 判定 | **达标**，比门槛（中位 1 s）快约 **227 倍** |

**口径要说清楚**：

- 这是**纯推理**，不含 wav 解码、重采样、裁/切、min-max——端到端时延要另测（ADR-032 要求两个都报）。
- 4.4 ms 已经包含不了什么余量问题：即使端到端再花几十毫秒，离 1 s 也有两个数量级。
- **不能直接和原文比**：Ma 等只写"100 个样本的推理在几十毫秒内完成"，没说是否含预处理、是否预热、什么机型什么后端。我们的 4.4 ms/窗 与它的"÷100 ≈ 亚毫秒"量级不同，**不可相减**。

对照（同一份模型，不同后端）：

| 平台 | 后端 | 单次推理 | 备注 |
| --- | --- | ---: | --- |
| 安卓 Edge（手机） | WebGL | **4.4 ms** | 真机，本文 |
| 本机（8 核 CPU） | CPU（Node） | 12 ms | 无 GPU 加速时的参考 |

### 9.4b 真 PWA：部署到 HTTPS，装到手机后离线可跑（2026-11-04）

之前那个 `http://` 页面**只是把算力放在手机上，文件仍每次从电脑取**——关掉电脑就打不开，
严格说不是 PWA。补齐 `manifest.json` + `sw.js`（预缓存 16 个文件）+ `icons/` 之后，部署到 HTTPS：

| 项 | 值 |
| --- | --- |
| 线上地址 | **https://dragon83599.github.io/FYP/** |
| 托管 | GitHub Pages，分支 `pwa-export`（`git subtree split --prefix=pwa`，20 个文件 / 1.8 MB）|
| 线上与本地逐文件 sha256 | `model.json`、`group1-shard1of1.bin`、`sw.js`、`app.js` **全部一致** |
| Content-Type | `app.js`/`sw.js` **application/javascript**、`model.json` application/json、权重 octet-stream（模块与 SW 都满足）|
| 手机端 | **已安装到桌面，关掉电脑 + 飞行模式下自检仍通过** |

**这一步的意义**：从此"端侧"不再依赖那台电脑。答辩现场可直接演示——把电脑合上、手机开飞行模式，
从桌面图标打开，仍有五类概率与 **1.88e-12** 的一致性结果。

时延（Node CPU 后端，单次）：模型加载 **12.9 ms**，首次推理 **39–77 ms**（含图构建）。
浏览器的 WebGL 后端与真机时延**尚未实测**，属于 W2 端上验收（中位 ≤1 s / P95 ≤2 s）的下一步。

**页面本身**也跑过一遍：`node tools/ai/tfjs-check/page-smoke.mjs` 用 DOM shim 执行 `pwa/app.js` 的真实代码路径，
结果是"模型已加载（20,193 参数）→ 自检通过：端到端最大差 1.19e-7"，两行一致性结果都渲染出来了。
**真实浏览器（WebGL 后端 + 渲染）仍未在本机验证**（无浏览器可装），这一项要现场打开页面确认；
静态完整性（元素 id、路径、参数量、参考 wav 存在）已进 CI（`npm test` 的 `tests/node/pwa-page.test.mjs`）。

### 9.5 可复算性（同 seed 两次跑，逐位相同）

加入 `set_determinism`（Python / NumPy / TF 三处播种，每折 `seed + k`）后，用**完全相同**的命令跑两次：

| 比较项 | 结果 |
| --- | --- |
| 十折准确率 | **完全相同**（98/100/99/97/100/100/98/97/98/99） |
| 每折 100 条测试样本的预测类别 | **完全相同** |
| 每折 5 类概率 | **最大差 = 0.0**（逐位相同） |
| 折的样本索引 | 完全相同 |

证明方式：`data/reports/repro-ma2023-seeded42-a` 与 `-b` 两份 `report.json` 对比。
**注意**：前三次 attempt（§9.1b 的 #1–#3）是在加入播种之前跑的，**不可逐位复算**，
它们代表"随机初始化下的波动"，正是 attempt 间 CI 要度量的东西；#4 才是可复算的那一版。
