# PWA 演示托管方案（W2 备用，2026-10-31）

> 目的：复核「手机端演示」在技术上怎么落地——**PPT 里只用「便携」做卖点，不用「扫码」**。
> **一条硬约束**：Service Worker（PWA 可安装/离线）**只在 HTTPS 或 localhost 下可用**。

## 1. 三种部署形态（按演示目的选）

| 形态 | 地址形态 | 能安装为 PWA | 实时采集（ws://）| 适用场景 |
| --- | --- | --- | --- | --- |
| **A 本机局域网** | `http://192.168.x.x:8080` | ❌（无 HTTPS）| ✅ | **答辩现场实时演示** |
| **B 静态托管** | `https://<user>.github.io/<repo>/` | ✅ | ❌（`ws://` 被混合内容拦截）| **老师自己手机验证文件输入** |
| **C 隧道** | `https://<random>.trycloudflare.com` | ✅ | ✅（需 `wss://`）| 两者都要，但依赖外网 |

## 2. 关键事实（易踩坑）

| 事实 | 后果 |
| --- | --- |
| `getUserMedia`（麦克风）需要安全上下文 | 形态 A 下**不能**用手机麦克风（我们本来也不用）|
| `ws://` 从 `https://` 页面发起 → **被拦截** | 形态 B **不能**做实时流 |
| TF.js + WebGL 在 http 页面正常工作 | 形态 A 的推理没问题 |
| iOS Safari 的「添加到主屏幕」需要 HTTPS | 形态 A 下 iPhone 无法安装 |
| 模型仅 **≈81 kB**（20,193 参数 float32）| 任何形态加载都很快 |

## 3. 建议的演示组合

| 环节 | 用哪种 | 一句话 |
| --- | --- | --- |
| 答辩主演示（实时）| **A** | 手机与队友设备连同一热点；页面 `http://` 打开；`ws://` 收流；现场看波形与概率 |
| 老师自测（文件）| **B** | 二维码指向托管地址；老师选一个 wav → 出五类概率 |
| 兜底 | 预录 wav | 网络异常时仍能出结果 |

**口径要准确**：
> **PPT 口径**：只说「**便携：手机随身带，无需额外设备**」——这是事实，且不依赖网络/托管。
> 下面三种形态仅供**实现与现场准备**用，不写进幻灯片。

## 4. 形态 A 的落地步骤（现场）

1. 队友设备开热点（或场地 Wi-Fi）。
2. 手机与笔记本连同一网络；笔记本起本地服务：`python -m http.server 8080`（或任意静态服务器）。
3. 手机浏览器打开 `http://<笔记本IP>:8080/`。
4. 页面内 `ws://<队友设备IP>:<port>` 收 320 B/20 ms 的 PCM。
5. 攒满 2 s → 推理 → 显示五类概率。

**风险**：场地 Wi-Fi 可能隔离客户端（AP isolation）→ **改用队友设备的热点**最稳。

## 5. 形态 B 的落地步骤（托管）

1. `tfjs.converters.save_keras_model()` 导出 `model.json` + `*.bin`。
2. 静态站点：`index.html` + `main.js` + `manifest.json` + `sw.js` + 模型目录。
3. 推到 GitHub Pages（或 Netlify 拖拽上传）。
4. 生成二维码指向该 URL；手机打开后「添加到主屏幕」。
5. **验证**：同一 wav 在 Python 与浏览器各跑一遍，概率差 <1e-3。

## 6. 与验收判据的关系

| 判据 | 在哪测 | 备注 |
| --- | --- | --- |
| 时延中位/P95 | 形态 A（真实页面）| 形态 B 也可，但测的是文件解码+推理 |
| 与 Python 一致性 <1e-3 | 形态 B | 用同一 wav，最容易复现 |
| 峰值内存 | 形态 A | 浏览器性能面板 |

## 7. 待确认

- [ ] 场地 Wi-Fi 是否隔离客户端（AP isolation）——决定用谁的热点。
- [ ] 队友设备能否同时提供音频流与热点（或改用笔记本当热点）。
- [ ] 是否需要 iPhone 现场演示（若要 → 必须形态 B 或 C）。
