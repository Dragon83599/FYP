# AI 模型资源预算入门

> 目标：让第一次训练模型的人能够把“我想做一个 AI”变成可计算的模型大小、
> 峰值 RAM、计算量、推理时延和芯片选择依据。

## 1. 先理解整个流程

```text
数据整理
  -> 预处理和切窗
  -> 训练集/验证集/测试集划分
  -> 训练基线模型
  -> 评估效果
  -> 量化为 int8
  -> 导出 ONNX/TFLite/CubeAI 等格式
  -> 在主机开发板实测
  -> 填写资源预算
  -> 选择主机芯片
  -> 固件集成和端到端测试
```

模型训练不是终点。最终决定主机能否使用的是目标板上的模型大小、峰值 RAM、
推理时间、功耗和并发能力。

## 2. 常用名词

| 名词 | 含义 | 对项目的影响 |
| --- | --- | --- |
| sample | 一个样本，例如一段 2 s 心音 | 数据量单位 |
| window | 模型一次输入的时间长度 | 决定输入样本数和延迟 |
| frame | 20 ms 的一小块连续音频 | 传输单位，不一定等于模型输入 |
| label | 样本标签，例如正常/异常 | 决定模型任务和评估指标 |
| epoch | 完整训练集训练一遍 | 训练次数单位 |
| batch | 一次送入模型的一组样本 | 影响训练显存和速度 |
| parameter | 模型可学习权重 | 决定模型大小 |
| MACs | 乘加运算次数 | 近似决定计算量 |
| FLOPs | 浮点运算次数，通常约为 2 x MACs | 比较模型规模 |
| int8 | 8-bit 整数量化 | 模型体积和计算量通常明显降低 |
| peak RAM | 推理时最高峰值内存 | 决定 MCU/SoC 是否够用 |
| latency | 一次推理耗时 | 决定结果显示是否及时 |
| throughput | 每秒可处理的窗口数 | 决定能否连续分析 |

## 3. 第一步：定义模型输入和输出

不要一开始就设计复杂网络，先固定数据契约：

```text
输入：4 kHz 单声道 PCM
窗口：例如 2 s = 8000 个样本
预处理：20~1000 Hz 带通、去直流、归一化
输出：例如正常/异常、S1/S2 或信号质量
```

窗口越长，感受野越大，但输入和计算量也越大。第一版建议：

- 2 s 或 3 s 窗口。
- 单通道。
- 4 kHz 重采样。
- 先做二分类或公共数据集已有的分类任务。

## 4. 第二步：准备数据

至少建立以下目录：

```text
dataset/
  raw/
  processed/
  splits/
  metadata.csv
```

必须遵守：

- 按患者或录音会话划分训练/验证/测试集，不能把同一患者的不同片段随机拆到两边。
- 记录采样率、时长、设备、患者编号、标签来源和数据授权。
- 保留原始数据，处理链可重复。
- 先做小数据集闭环，不要等所有数据整理完才训练。
- 训练集、验证集、测试集的预处理参数必须一致。
- 不把测试集用于调参。

## 5. 第三步：先做基线模型

第一版不要上 Transformer。建议顺序：

1. 特征 + 逻辑回归/SVM：验证数据标签和流程。
2. 小型 1D CNN：通常最适合心音波形。
3. ResNet/TCN：基线不足时再增加容量。
4. 轻量 Transformer：数据量和计算预算都充足时再考虑。

第一版目标不是追求最高准确率，而是得到可测量的模型：

```text
训练可完成
验证指标可解释
可以导出
可以量化
可以在目标板运行
```

## 6. 第四步：评估模型

不要只看准确率。至少输出：

- 混淆矩阵。
- 敏感度和特异度。
- Precision、Recall、F1。
- AUROC。
- 按患者分组的误差。
- 不同噪声和信号质量下的误差。
- 模型错误样本的波形。

## 7. 第五步：量化

常见顺序：

```text
FP32 训练
  -> 训练后量化 int8
  -> 代表性数据校准
  -> 量化敏感度分析
  -> 必要时量化感知训练
```

需要记录：

- int8 模型文件大小。
- 量化前后指标变化。
- 权重和激活的量化范围。
- 目标推理框架是否支持网络中的算子。

## 8. 第六步：计算资源预算

### 8.1 模型文件大小

近似公式：

```text
FP32 size ~= parameters x 4 bytes
FP16 size ~= parameters x 2 bytes
INT8 size ~= parameters x 1 byte
```

实际文件还要加上常量、元数据和对齐开销。

### 8.2 峰值 RAM

峰值 RAM 不等于模型文件大小，至少包括：

```text
权重或权重缓存
输入张量
中间激活
算子工作区
推理框架开销
双缓冲和对齐余量
```

峰值 RAM 必须用目标推理框架的 profiler 或开发板 heap 统计测量，不能只用
模型大小估算。

### 8.3 MACs 和 FLOPs

使用 `torchinfo`、`ptflops`、ONNX profiler 或推理框架自带工具记录：

```text
每个窗口的 MACs
每个窗口的 FLOPs
每秒钟需要的窗口数
```

例如模型每秒处理 0.5 个 2 s 窗口，则平均 MACs/s = 单窗口 MACs x 0.5。

### 8.4 推理时延和峰值电流

在主机开发板上测量：

| 指标 | 测量方法 |
| --- | --- |
| 推理时间 | 目标板计时 100~1000 次，记录平均/P95/最大 |
| 峰值 RAM | 推理前、推理中、推理后的 heap 记录 |
| 峰值电流 | 功率分析仪或电流探头 |
| 平均功耗 | 单次测量和连续测量分别记录 |
| 帧率 | 屏幕实际刷新的结果不是理论值 |
| 丢帧 | 推理期间继续接收 BLE 和显示音频 |

## 9. 主机平台的决策门槛

候选平台和最终资源门槛必须一起决定：

| 平台 | 适合条件 | 主要限制 |
| --- | --- | --- |
| ESP32-S3 | int8 模型较小、显示和 AI 需求中等、需要快速原型 | 无 NPU、只有 2.4 GHz Wi-Fi，和 BLE 共存需实测 |
| ESP32-P4 + C5/C6 | 模型和 UI 更大、需要 MIPI 显示、希望 2.4/5 GHz | 两颗芯片，软件和 PCB 复杂度上升 |
| STM32N6 + 无线模块 | 模型需要使用 NPU 或 600 GOPS 级能力 | 无线需外接，工具链和集成复杂度更高 |
| Linux SoC | 可接受更高功耗、电池和启动时间，AI/GUI 最优先 | 实时性、续航和功耗通常最差 |

建议预算必须提供至少 30% 余量。以下门槛只能作为候选值，最终必须用实际
模型和开发板验证：

```text
模型文件：优先小于可用 Flash/PSRAM 的 50%
峰值 RAM：小于可用内存的 70%
推理时延：P95 小于允许显示更新周期的 50%
BLE 接收：推理时不能持续丢帧
Wi-Fi：上传或同步时不能阻塞推理和显示
```

## 11. 建议的第一轮任务

1. 选定一个公开心音数据集，先只取少量样本跑通流程。
2. 做 2 s、4 kHz、单通道的输入管线。
3. 训练一个小型 1D CNN 基线。
4. 记录参数量、INT8 模型大小、MACs 和 PC 推理时间。
5. 导出 ONNX 或 TFLite，做训练后 INT8 量化。
6. 在一张主机候选开发板上运行模型。
7. 同时打开 BLE 接收、Wi-Fi 和显示，测量峰值 RAM、延迟和电流。
8. 根据实测结果填写本文件模板，再更新 ADR-006。

## 12. 常见错误

- 先买芯片，再训练模型。正确顺序是先得到模型预算，再选平台。
- 把模型文件大小当成峰值 RAM。两者不是一回事。
- 用 PC 推理时间推断 MCU 时间。必须用目标板实测。
- 只用准确率，不做患者级测试集划分。
- 不做 INT8 量化，直接假设模型能放进 MCU。
- 忽略 BLE、Wi-Fi、显示和音频回放的并发影响。
- 在推理期间让 CPU 阻塞，导致采集丢帧。
